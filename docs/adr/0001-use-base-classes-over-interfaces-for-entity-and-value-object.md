# 0001. Entity/ValueObjectはインターフェースではなく基底クラスにする

## ステータス

Accepted

## コンテキスト

`BuildingBlocks`ライブラリで、DDDの戦術的パターンであるEntityとValueObjectの
共通基盤を提供したい。実装の与え方として、インターフェース(`IEntity<TId>`など)と
基底クラス(`Entity<TId>`など)の2通りが考えられた。

## 検討した選択肢

- **インターフェースにする**: `IEntity<TId>` / `IValueObject`のようなマーカー的
  インターフェースを提供し、`Equals`/`GetHashCode`/`==`の実装は利用側のクラスに
  委ねる案。継承の枠を消費しないという利点がある。

- **基底クラスにする**: `Entity<TId>` / `ValueObject`を抽象基底クラスとして提供し、
  等価性の実装そのものを基底クラス側に持たせる案。

## 決定

基底クラスを採用する。

「エンティティはIdで同一性が決まる」「値オブジェクトは構成要素で同一性が決まる」
というのは、そのオブジェクトが何であるかを定義する**契約**であり、単なる
「振る舞いの再利用」ではない。インターフェースにすると、この契約の実装を
利用側に委ねることになり、`GetType()`比較の書き忘れやハッシュ計算のミスといった
同種の不具合が実装ごとに再発するリスクがある。

さらにC#の言語仕様上、`Equals`のオーバーライドや`==`演算子の定義はインスタンス
メソッドとしてクラス自身が実装する必要があり、インターフェース + 委譲だけでは
演算子の呼び出しをフックできない。委譲コードを毎回書かせるくらいなら、
契約ごと基底クラスに閉じ込める方が「実装者が正しく書く」ことに依存しない。

## 結果・トレードオフ

- 等価性の契約が型システムで保証され、利用側での実装ミスが構造的に防がれる。
- 一方で、`Entity<TId>`/`ValueObject`を継承した時点で、C#の単一継承の制約により
  そのクラスは他のクラスをこれ以上継承できなくなる。この点は
  [ADR-0002](./0002-restrict-inheritance-to-entity-and-value-object-only.md)で
  別の設計判断として積極的に採用している。
