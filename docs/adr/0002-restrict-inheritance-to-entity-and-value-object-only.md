# 0002. ドメイン層での継承はEntity/ValueObjectの契約を満たす1段階のみに限定する

## ステータス

Accepted

## コンテキスト

[ADR-0001](./0001-use-base-classes-over-interfaces-for-entity-and-value-object.md)
により、ドメインクラスは`Entity<TId>`または`ValueObject`を継承することが基本形になる。
C#は単一継承のため、この時点でそのクラスの継承の枠は使い切られる。

このとき、ドメインクラス同士でさらに継承関係(例: 支払い方法の多態性を表現するために
`Payment`という基底クラスを作り、`CreditCardPayment : Payment`とする)を作ってよいか
どうかを明確にしておく必要があった。「継承よりコンポジション」という一般原則との
整合性も併せて整理したい。

## 検討した選択肢

- **ドメインクラス間の継承も許容する**: `Payment`のような中間基底クラスを許し、
  `CreditCardPayment : Payment`とする。C#的には`Payment`自体が`Entity<TId>`を
  継承していれば1段階で済むケースも多く、実用上大きな問題は起きにくい。

- **ドメインクラス間の継承を原則禁止し、多態性はインターフェースで表現する**:
  `Payment`という基底クラスを作らず、`IPayment`のようなインターフェースを
  `CreditCardPayment : Entity<Guid>, IPayment`のように実装させる。共通の状態
  (金額や日時など)が必要な場合は、共有のValueObject(例: `PaymentDetails`)を
  各クラスがコンポジションとして保持する。

## 決定

後者(継承を1段階に限定し、多態性はインターフェースで表現する)を採用する。

「継承よりコンポジション」の原則が本来問題にしているのは、is-aの関係が
実は成立していないのに振る舞いの再利用のためだけに継承を使うケースである。
`Entity<TId>`/`ValueObject`の継承は「同一性の契約」を満たすためのものであり、
この原則が想定する濫用には当たらない。一方で、ドメインクラス同士がさらに
継承関係を作ろうとする場合は、多くが「振る舞いや状態の共有」を目的としており、
この原則が本来警戒している状況に該当しやすい。

そのため、
> ドメイン層で継承を使ってよいのは`Entity`/`ValueObject`の契約を満たす1段階のみ。
> 多態性はインターフェースで表現し、共通の状態はコンポジションで持たせる。

という原則をチームのルールとして採用する。

## 結果・トレードオフ

- ドメインモデルの継承ツリーが常に浅く保たれ、「共通処理をなんとなく親クラスに
  寄せる」という設計の劣化を構造的に防げる。
- `Payment`のような中間基底クラスを作れない分、共通のバリデーションロジックなどは
  拡張メソッドや、共有のValueObjectのメソッドとして持たせる必要があり、
  設計の手数がわずかに増える。
- 「継承の枠を使い切っているから仕方なくコンポジションを使う」という消極的な
  理由ではなく、「同一性の契約(継承)」と「多態性・データの再利用(合成)」を
  最初から意図的に分離する、という積極的な設計判断として位置づけている。
