# 0003. Errorはrecordではなく自前実装のstructにする

## ステータス

Accepted

## コンテキスト

`Results`ライブラリで、失敗の理由を表現する`Error`型が必要になった。
`Error`は`Code`(識別子)と`Message`(人間向け説明)の2フィールドからなる、
不変条件を持たない単純な値であり、構造的等価性(全フィールドが等しければ
同一とみなす)を持たせたい。

実装当初はC#の`record struct`機能を使って実装していたが、
`BuildingBlocks`の`ValueObject`は同じ「構造的等価性を持つ値」でありながら
自前でEquals/GetHashCodeを実装しており、両者の間に一貫性の欠如があることに
気づいた。

## 検討した選択肢

- **`record struct`を使う**: `Equals`/`GetHashCode`/`==`/`!=`/`ToString`が
  自動生成され、コード量を大幅に削減できる。C#では一般的で読み手にも
  馴染みがある。

- **自前実装にする**: `ValueObject`と同じ方針で、`IEquatable<Error>`を
  手動実装する。

## 決定

自前実装を採用する。

このリポジトリの目的は「C#の便利機能に頼らず、言語を問わず通用する設計思考を
見せること」であり、`ValueObject`ではその方針のもとに自前実装を選んでいる。
`Error`だけ`record`という言語機能に頼ると、同じ性質の型に対して
「片方は自作、片方は言語機能任せ」という説明のつかない使い分けが生まれ、
このリポジトリ全体の一貫性という一番の価値を損なう。

`record`が持つ「コード量の削減」「レビューコストの低減」というメリット自体は
実務上十分に合理的であり、チームの合意次第では積極的に採用してよいと考えている。
今回はポートフォリオとしての一貫性を優先した、という位置づけである。

## 結果・トレードオフ

- `ValueObject`と`Error`が同じ設計方針(自前実装)で統一され、
  「ここは自作、ここは言語機能」という説明の手間がなくなった。
- `record`を使った場合と比べてコード量は増える(`Equals`/`GetHashCode`/
  演算子の実装が必要)。単純なDTOとしては見た目上やや冗長になる。
- 実務でこの判断をそのまま採用するかどうかはチームの状況次第であり、
  「一貫性を優先するか、コード量を優先するか」はプロジェクトごとに
  再検討されるべきトレードオフである。
