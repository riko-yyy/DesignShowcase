# BuildingBlocks

クリーンアーキテクチャにおけるドメイン層でのモデリングを想定した、
`Entity` / `ValueObject` / `IAggregateRoot` の3点セットを提供する軽量ライブラリです。

外部フレームワーク(EF Core, JSON関連の属性など)への依存は一切持ちません。

## 提供するもの

| 型 | 役割 |
|---|---|
| `Entity<TId>` | Idによって同一性が決まるオブジェクトの基底クラス |
| `ValueObject` | 構成要素によって同一性が決まるオブジェクトの基底クラス |
| `IAggregateRoot` | 集約ルートであることを示すマーカーインターフェース |

## なぜ基底クラスなのか(インターフェースにしなかった理由)

`IEntity<TId>`のようなインターフェースにする案も検討しましたが、採用しませんでした。

インターフェースにすると、`Equals` / `GetHashCode` / `==` の実装を
利用する側のクラスが毎回書くことになります。しかしこれらは
「エンティティはIdで同一性が決まる」「値オブジェクトは構成要素で同一性が決まる」という、
**そのオブジェクトが何であるかを定義する契約そのもの**です。契約であるにもかかわらず
実装を各クラスに委ねてしまうと、`GetType()`比較の書き忘れやハッシュ計算のミスといった
同じ種類の不具合が実装ごとに再発するリスクがあります。

加えてC#の言語仕様上、`Equals`系のオーバーライドはインスタンスメソッドとしてクラス自身が
実装する必要があり、インターフェース+委譲だけでは`a == b`のような演算子呼び出しを
フックできません。委譲コードを毎回書かせるくらいなら、契約ごと基底クラスに閉じ込めた
方が「実装者が正しく書く」ことに依存しない設計になります。

## 継承はEntity/ValueObjectのためだけに使う

C#は単一継承のため、`Entity<TId>`または`ValueObject`を継承した時点で、
そのクラスは他のクラスをこれ以上継承できません。これは制約ではなく、
意図的なルールとして採用しています。

> ドメイン層で継承を使ってよいのは、`Entity<TId>` / `ValueObject`の契約を
> 満たすための1段階のみ。多態性が必要な場面は`Payment`のような基底クラスではなく
> `IPayment`のようなインターフェースで表現し、共通の状態が必要であれば
> 専用のValueObjectなどをコンポジションで持たせる。

例えば支払い方法を表現したい場合、`Payment`という基底クラスは作らず、
`CreditCardPayment : Entity<Guid>, IPayment` のように
「同一性の契約」と「多態性のための型」を分けて持たせます。共通のプロパティ
(金額や日時など)が必要であれば、共有のValueObject(例: `PaymentDetails`)を
各クラスがコンポジションとして保持する形にします。

これにより、「継承の枠を使い切っているから仕方なくコンポジションを使う」という
消極的な理由ではなく、「同一性の契約(継承)」と「多態性・データの再利用(合成)」を
最初から意図的に分離する、という設計判断として一貫させています。

## 意図的に含めていないもの

- ドメインイベントの蓄積機構 — 必要になった時点で `IHasDomainEvents` のような
  形で拡張する想定。最初から持たせて「使わない機能」を持ち込まない方針。
- リポジトリインターフェースなどの永続化に関するもの — このライブラリの責務外。
