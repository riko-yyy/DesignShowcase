# Design Showcase — 言語非依存の設計思考を形にする

[![CI](https://github.com/riko-yyy/DesignShowcase/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/riko-yyy/DesignShowcase/actions/workflows/ci.yml)

> C# の実務経験で培った「構造設計」の考え方を、特定言語・特定フレームワークへの依存を極力排除した形で実装したものです。
> ここにあるコードはC#で書かれていますが、伝えたいのは**C#の書き方ではなく、どの言語でも通用する設計上の判断軸**です。

## なぜこれを作ったか

実務では既存システムの制約やチームの慣習の中でコードを書くことが多く、「自分がゼロから設計するとしたらどう考えるか」を見せる機会は意外と少ないです。

このリポジトリは、以下を証明するために作りました。

- 例外的なフレームワーク機能に頼らず、素のオブジェクト指向/一部関数型的な考え方で設計できること
- 「変更に強い」「テストしやすい」構造を意識的に作れること
- 複数の小さなライブラリを一貫した思想のもとに組み合わせられること

## 全体構成

```
src/
├── BuildingBlocks/   ドメインモデリングの基盤 (Entity / ValueObject など)
├── Results/          例外に頼らないエラーハンドリングのためのResult型
└── Pricing/          ルール合成による料金計算エンジン (割引/加算どちらにも応用可)

samples/
└── SampleApp/        上記3つを組み合わせた実用フロー例

tests/
└── (各ライブラリに対応するユニットテスト)
```

3つは独立して使えるライブラリですが、`Pricing` は内部で `Results` を利用しており、`SampleApp` では「入力検証 → ドメインオブジェクト生成 → 料金計算」という一連の業務フローを通して、3つがどう連携するかを示しています。

## 設計思想として意識していること

このリポジトリ全体を通じて、特定の言語機能よりも以下の原則を優先しています。

| 原則 | 具体的にやっていること |
|---|---|
| 依存の方向を制御する | ドメインロジックはインフラや外部フレームワークに依存しない |
| 副作用と判断ロジックを分離する | 「何が起きるか」と「どう判断するか」を別クラスに分ける |
| 変更に閉じた設計 | 新しいルールを追加する際、既存コードの修正が不要になる構造 |
| 失敗を型で表現する | 想定内の失敗（業務ルール違反など）は例外ではなく戻り値として扱う |

各ライブラリのREADMEでは、なぜその粒度で抽象化を止めたか、どんなトレードオフを選んだかについても記載しています。

## 設計判断の記録(ADR)

各ライブラリの個別READMEに加えて、設計上の決定とその検討過程を[`docs/adr/`](./docs/adr/)にArchitecture Decision Recordとして残しています。
「なぜこの設計にしたか」だけでなく「他にどんな案を検討し、なぜ却下したか」も記録しているので、コードだけでは伝わらない判断の過程はこちらを参照してください。

## 各ライブラリ

- [`BuildingBlocks`](./src/BuildingBlocks/README.md) — Entity/ValueObjectの基底クラスとインターフェース
- [`Results`](./src/Results/README.md) — 例外を使わないエラーハンドリングのためのResult型
- [`Pricing`](./src/Pricing/README.md) — ルールを合成して料金を算出するエンジン

## 動かし方

```bash
dotnet build
dotnet test
```

`samples/SampleApp` は3つのライブラリを組み合わせた最小限のコンソールアプリです。
実際の業務フローに近い形で、各ライブラリがどう協調するかを確認できます。
